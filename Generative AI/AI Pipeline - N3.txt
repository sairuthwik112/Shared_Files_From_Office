Encoder–Decoder Model (Simple Explanation)
The model takes an input sentence (example: “The cat ate the mouse”).
The sentence is read one word at a time.
While reading, the model keeps a memory of what it has understood so far.
This memory is called the hidden state.
Hin means the memory coming into the current word.
The model reads the current word and updates the memory.
The updated memory is called Hout.
This Hout is passed to the next word as its Hin.
After the last word, the final hidden state contains the meaning of the full sentence.
This final memory is passed to the decoder.
The decoder starts with a special GO token.
Using the memory, the decoder generates one output word at a time.
After generating each word, the decoder updates its memory.
The decoder continues generating words until it produces an END token.
The final generated words form the output sentence (example: translation, summary, answer).
This whole process is called sequence‑to‑sequence learning.
Modern LLMs (Gemini, GPT) already have this architecture built in.
We learn this mainly to understand how LLMs work, not to build it ourselves.

Encoder–decoder is an older architecture concept, and Transformers are the modern models that use this concept to translate text more efficiently.

Vector Search

1.Vector search starts by converting raw data such as text into numerical vectors
2.Initially simple methods like one‑hot encoding convert words into binary vectors
3.One‑hot encoding creates a matrix with 1 at the word position and 0 elsewhere
4.One‑hot encoding does not capture relationships or meaning between words
5.To capture semantic meaning we use text embedding models
6.Text embedding models convert sentences into dense numerical vectors
7.Similar meanings are represented by vectors close to each other
8.All generated vectors are stored along with their metadata
9.The vectors are indexed in a vector space to enable fast search
10.A vector search index is created to organize vectors efficiently
11.When a query is given the query text is converted into a vector
12.The query vector is compared with stored vectors in the index
13.Vector similarity is calculated using distance or similarity measures
14.Common distance metrics include Euclidean distance and Manhattan distance
15.Other similarity measures include cosine similarity and dot product
16.The goal is to find vectors that are closest to the query vector
17.Vector search algorithms are used to find nearest neighbors
18.Brute force search compares the query vector with all vectors
19.Brute force gives accurate results but is slow for large datasets
20.Approximate Nearest Neighbor algorithms improve search speed
21.Tree‑based and graph‑based indexing methods are commonly used
22.These ANN methods reduce computation while keeping good accuracy
23.The system retrieves the top‑K most similar vectors
24.The associated data items are returned as search results
25.In BigQuery the process starts with generating text embeddings
26.Embeddings are stored and indexed using BigQuery vector search
27.A vector search index is created inside BigQuery
28.An endpoint is created to serve vector search queries
29.A user query is converted into an embedding
30.BigQuery runs a vector search query using the index
31.The system returns the most relevant results based on vector similarity

1.Text is converted into embeddings using a pretrained Transformer encoder model
2.The text is first tokenized into words or sub words
3.Each token is mapped to an initial numerical representation
4.These representations pass through multiple Transformer encoder layers
5.Attention mechanisms adjust values based on context and meaning
6.The final encoder layer outputs a dense numerical vector
7.This vector is called the text embedding
8.Each number in the embedding represents a learned semantic feature
9.Individual numbers have no direct human meaning
10.Meaning is captured when vectors are compared to each other
11.The embedding model outputs a fixed‑length vector for every input
12.In this model the fixed length is 768 dimensions
13.768 is a design choice of the model architecture
14.It balances semantic richness and computational efficiency
15.All words sentences and documents use the same 768‑length vector
16.This is required so similarity and distance can be calculated
17.The values are usually normalized and lie between -1 and 1
18.Normalization helps with stable similarity calculations
19.When printing embeddings only the first 10 values are shown
20.This is done only for readability and debugging
21.The full 768 values are still present and used internally
22.Printing all values would be too long and not useful
23.Word embeddings and sentence embeddings have the same length
24.The same embedding space allows fair comparison
25.Vector search uses the full embedding not the first 10 values
26.Distance or similarity is calculated using all 768 dimensions
27.This is how semantic similarity is measured in vector search and RAG
